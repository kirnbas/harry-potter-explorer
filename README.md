# ⚡ Harry Potter Explorer

Веб-приложение для исследования вселенной «Гарри Поттера»: факультеты, персонажи,
заклинания и магические артефакты. Написано на **ASP.NET Core MVC (.NET 10)** без
клиентских фреймворков и без сборщика — сервер рендерит HTML, а браузер добавляет ровно
три вещи, которые без него не работают: личную коллекцию карточек, бесконечную прокрутку
и живую ленту событий.

**Живое демо:** https://harry-potter-explorer-mm3q.onrender.com/ · **Репозиторий:** https://github.com/kirnbas/harry-potter-explorer

## Соответствие техническому заданию

### Уровень 1 — Базовый интерфейс ✅

Навигация по всем разделам, атмосферная главная страница, страница со списком всех
четырёх факультетов и отдельная страница каждого факультета с цветами, символикой и
описанием.

### Уровень 2 — Динамические данные и поиск ✅

- Данные о персонажах берутся из [hp-api.onrender.com](https://hp-api.onrender.com/).
- **Внешний API вызывается только с сервера.** Единственное место в решении, которое
  знает адрес внешнего сервиса, — типизированный `HttpClient` в
  [`Services/HarryPotterApiClient.cs`](HarryPotterExplorer/Services/HarryPotterApiClient.cs).
  Браузер обращается исключительно к собственным эндпоинтам `/api/*` и `/characters/cards`.
- Каталог показывает изображение, имя, факультет и патронус.
- Поиск по имени — а также по альтернативным именам и по имени актёра
  (`«The Chosen One»` → Harry Potter, `«Rickman»` → Severus Snape,
  `«Luna»` → Luna Lovegood и Lily Potter, у которой альтернативное имя *Lily Luna Potter*).
- Ленивая подгрузка на `IntersectionObserver` + кнопка «Summon more cards» как запасной
  путь; серверная пагинация с метаданными в заголовках ответа.

### Уровень 3 — Публичный доступ ⚙️

В репозитории лежат готовые `Dockerfile`, `.dockerignore` и `render.yaml`.
См. раздел [Деплой](#деплой) — развёртывание сводится к «подключить репозиторий к Render».

## Технический стек и почему именно он

| Слой | Выбор | Почему |
|---|---|---|
| Платформа | **.NET 10 / ASP.NET Core MVC** | Требование «внешние сервисы вызываются с сервера» — это по сути требование к серверному рендерингу и серверному слою интеграции. MVC даёт это из коробки: контроллеры, Razor-представления, DI, `IHttpClientFactory`, `BackgroundService` и SignalR — всё в одном рантайме, без второго процесса на Node |
| Данные | **SQLite + EF Core 10** | Проект должен запускаться сразу после `git clone` — без Docker Compose, без учётных данных, без облачного проекта. SQLite это даёт: файл создаётся при первом старте и наполняется сам. EF Core берёт на себя схему, миграцию типов и LINQ-запросы |
| Реальное время | **SignalR** | Встроен в ASP.NET Core: не нужен внешний realtime-провайдер и его ключи. WebSocket с автоматическим падением до SSE/long-polling и переподключением — это ровно то, что нужно странице `/live` |
| Устойчивость HTTP | **Microsoft.Extensions.Http.Resilience** (Polly) | Внешний API живёт на бесплатном инстансе Render и «засыпает». Стандартный обработчик даёт ретраи, таймауты и circuit breaker декларативно, вместо самописного `for`-цикла |
| Фронтенд | **Ванильный JS + собственный CSS** | Единственная действительно клиентская логика — коллекция в `localStorage`, бесконечная прокрутка и SignalR. Ради этого тянуть React и сборку — это оверинжиниринг: страница осталась бы серверной, но появилась бы вторая система сборки и второй язык шаблонов. Итог: **ноль npm-зависимостей в рантайме**, кроме vendored-клиента SignalR |
| Шрифты и иконки | **Системные шрифты + эмодзи** | Ни одного запроса к Google Fonts или CDN-иконкам: страница выглядит одинаково офлайн, быстрее грузится и не отдаёт данные посетителя третьим сторонам |

**Почему не Supabase / Firebase.** Оба они дали бы realtime «из коробки», но привязали бы
запуск проекта к чужому аккаунту и ключам: проверяющий не смог бы просто склонировать
репозиторий и нажать «запустить». SQLite + SignalR дают тот же наблюдаемый результат —
данные выгружены в базу, изменения видны в реальном времени — но без единого секрета в
конфигурации.

## Быстрый старт

Нужен только [.NET SDK 10](https://dotnet.microsoft.com/download).

```bash
git clone <адрес-вашего-репозитория>
cd HarryPotterExplorer
dotnet run --project HarryPotterExplorer --launch-profile http
```

Откройте <http://localhost:5076>.

При первом запуске приложение:

1. создаёт `HarryPotterExplorer/App_Data/hogwarts.db`;
2. загружает 24 артефакта из `SeedData/artifacts.json`;
3. **в фоне** обращается к внешнему API и записывает 437 персонажей и 77 заклинаний.

Шаг 3 выполняется после того, как сайт уже начал отвечать, поэтому главная страница
открывается мгновенно. Если внешний API «просыпается» (холодный старт Render занимает до
минуты), на страницах видно честное сообщение «The owls are still flying» — обновите её
через минуту.

### В Docker

```bash
docker build -t hpx . && docker run -p 8080:8080 hpx
```

### Полезные команды

```bash
dotnet build
```

```bash
curl -s http://localhost:5076/api/stats
```

```bash
curl -s -X POST http://localhost:5076/api/sync
```

### Конфигурация

Всё настраивается через `appsettings.json` или переменные окружения:

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `ConnectionStrings:Hogwarts` | `Data Source=App_Data/hogwarts.db` | Путь к файлу БД |
| `HarryPotterApi:BaseAddress` | `https://hp-api.onrender.com/` | Адрес внешнего API |
| `HarryPotterApi:TimeoutSeconds` | `100` | Таймаут запроса (запас на холодный старт) |
| `HarryPotterApi:RetryCount` | `3` | Число повторов |
| `HarryPotterApi:RefreshIntervalHours` | `6` | Периодичность фонового обновления |
| `PORT` | — | Если задана, приложение слушает `0.0.0.0:$PORT` (Render, Railway, Fly) |

## Архитектура

```
                    ┌──────────────────────────────┐
   Браузер          │  hp-api.onrender.com         │
      │             │  (внешний публичный API)     │
      │             └──────────────┬───────────────┘
      │                            │  ← только сервер, только исходящие
      │                            │     запросы, только в фоне
      │             ┌──────────────┴───────────────┐
      │             │  CatalogSyncBackgroundService│
      │             │  + CatalogSyncCoordinator    │
      │             │  (ретраи, circuit breaker,   │
      │             │   upsert, журнал синхронизаций)
      │             └──────────────┬───────────────┘
      │                            ▼
      │                    ┌───────────────┐
      │                    │ SQLite / EF   │  ← единственный источник данных
      │                    │ Core          │     для всех страниц
      │                    └───────┬───────┘
      │                            ▼
      │             ┌──────────────────────────────┐
      ├── HTML ─────┤  Razor-представления         │
      ├── JSON ─────┤  /api/*  (CatalogApiController)
      ├── HTML-фрагменты ── /characters/cards, /spells/rows
      └── WebSocket ┤  SignalR-хаб /hubs/great-hall│
                    └──────────────────────────────┘
```

**Ключевая идея — «зеркалировать, а не проксировать».** Наивная реализация проксирует
каждый запрос пользователя во внешний API. Это означает: медленный поиск, зависимость от
доступности чужого сервиса, невозможность фильтровать и сортировать (внешний API отдаёт
всё одним массивом без пагинации) и риск получить 429. Вместо этого фоновая служба один
раз выгружает весь набор данных в собственную базу и обновляет его раз в 6 часов. В
результате:

- поиск и фильтрация — обычные SQL-запросы с индексами;
- сайт продолжает работать, когда внешний API недоступен (страница честно сообщает
  состояние: `ready` / `syncing` / `stale` / `failed`);
- ровно два исходящих HTTP-запроса на цикл обновления вместо одного на каждого посетителя.

## Публичный HTTP API

Все данные, которые видит браузер, доступны и как JSON:

| Метод и путь | Описание |
|---|---|
| `GET /api/characters` | Поиск и пагинация. Параметры: `search`, `house`, `species`, `role`, `status`, `sort`, `page`, `pageSize`, `withImage` |
| `GET /api/characters/{id}` | Полная карточка персонажа |
| `POST /api/characters/by-ids` | Гидратация локальной коллекции (тело — массив id) |
| `GET /api/spells` | Заклинания: `search`, `category`, `page`, `pageSize` |
| `GET /api/artifacts` | Артефакты: `search`, `category` |
| `GET /api/houses` | Лор факультетов + количество участников |
| `GET /api/facets` | Списки значений для фильтров |
| `GET /api/stats` | Агрегаты, топ коллекционируемых, последние события, статус синхронизации |
| `GET /api/sync` · `POST /api/sync` | Состояние зеркала / внеочередное обновление |
| `POST /api/collection/{id}` | Отметить карточку собранной или отпущенной |
| `POST /api/sorting-hat` | Подсчёт результатов квиза |

Пример:

```bash
curl -s "http://localhost:5076/api/characters?search=weasley&sort=house&pageSize=5"
```

## Процесс проектирования и разработки

**1. Разведка данных до написания кода.** Первым делом был вызван внешний API и изучен
реальный ответ — 437 объектов с неоднородными полями: `alternate_names` в snake_case
рядом с `dateOfBirth` в camelCase, `wand` иногда пустой объект `{}`, `dateOfBirth` то
`null`, то пустая строка, часть URL изображений отдаёт 404. Это сразу определило три
решения: отдельные DTO для внешнего контракта, нормализацию «пустая строка → `null`» и
клиентский фолбэк для битых картинок.

**2. Выбор стратегии интеграции.** Требование «внешние сервисы вызываются с серверной
части» можно выполнить формально — тонким прокси. Но внешний API не поддерживает ни
пагинацию, ни поиск, а живёт на засыпающем бесплатном инстансе. Отсюда родилась схема
«зеркало»: фоновая служба + собственная БД. Это же автоматически закрыло бонусное
требование про выгрузку данных в базу.

**3. Схема БД от запросов, а не от источника.** Таблицы спроектированы под то, что
реально нужно страницам: денормализованное поле `SearchIndex` (заранее приведённое к
нижнему регистру склеенное имя + альтернативные имена + актёр), индексы по `House`,
`Name`, `SearchIndex`. Счётчики коллекции вынесены в отдельную таблицу `CharacterStats`,
а события — в неизменяемый журнал `LedgerEvents`, потому что у них разный жизненный цикл:
счётчик перезаписывается, событие только добавляется.

**4. Сначала сервер, потом браузер.** Каждая страница была сделана полностью рабочей на
сервере, и только затем поверх добавлялся JavaScript. Поэтому каталог персонажей
индексируется поисковиками, открывается без JS и не «мигает» скелетоном при первой
загрузке.

**5. Проверка вручную по ходу работы.** Каждый слой проверялся в браузере сразу после
написания: синхронизация (437 персонажей, 77 заклинаний в логах), поиск по альтернативным
именам и актёрам, бесконечная прокрутка (24 → 48 → 72 → 96 карточек), полный цикл
коллекции (`localStorage` → API → БД → SignalR → лента), идемпотентность повторного
нажатия, адаптивная вёрстка на 375 px. Так были найдены и исправлены две настоящие
ошибки — они описаны ниже.

## Уникальные подходы и решения

### HTML вместо JSON для подгружаемых карточек

Классическая проблема бесконечной прокрутки: разметка карточки существует дважды — в
серверном шаблоне для первой страницы и в JS-шаблоне для последующих. Со временем они
расходятся.

Здесь эндпоинт `GET /characters/cards` возвращает **HTML-фрагмент**, отрендеренный тем же
частичным представлением [`_CharacterCard.cshtml`](HarryPotterExplorer/Views/Shared/_CharacterCard.cshtml),
что и первая страница, а метаданные пагинации едут в заголовках `X-Total-Count`,
`X-Has-More`, `X-Page`. Клиентский код сводится к `grid.insertAdjacentHTML(...)` — шаблон
карточки в проекте ровно один. Тот же приём применён для списка заклинаний
(`/spells/rows`) и для гидратации альбома (`POST /characters/cards/by-ids`).

При этом полноценный JSON API (`/api/*`) никуда не делся — он существует параллельно для
внешних потребителей.

### Разделение приватного и публичного в «избранном»

`localStorage` хранит **список** карточек — он никогда не покидает браузер. Сервер узнаёт
только факт «кто-то собрал карточку X», помеченный анонимным идентификатором браузера в
first-party cookie. Этого достаточно, чтобы:

- показывать общий счётчик и топ коллекционируемых персонажей;
- не давать одному браузеру накрутить счётчик повторными нажатиями (сервер сравнивает
  запрошенное действие с последним записанным и игнорирует дубликат);
- при этом не иметь ни аккаунтов, ни персональных данных.

Так одно решение закрывает сразу два бонусных пункта — «избранное в localStorage» и
«данные в БД с просмотром в реальном времени» — и они усиливают друг друга, а не живут
отдельными демо.

### Обогащение данных на нашей стороне

Внешний API отдаёт заклинание как «имя + одна строка описания» — плоский несортируемый
список. [`SpellClassifier`](HarryPotterExplorer/Services/SpellClassifier.cs) при
синхронизации проставляет каждому заклинанию категорию (Charm, Curse, Jinx, Hex,
Transfiguration, Healing…), а три Непростительных заклятия выделены отдельно. Категории
становятся фильтром и цветной меткой на странице. Аналогично артефакты — целый раздел,
которого во внешнем API нет вовсе, — курированы вручную и лежат в
[`SeedData/artifacts.json`](HarryPotterExplorer/SeedData/artifacts.json): чтобы дописать
лор, достаточно отредактировать JSON.

### Логика квиза скрыта на сервере

Веса ответов Распределяющей шляпы живут в
[`SortingHatService`](HarryPotterExplorer/Services/SortingHatService.cs) и никогда не
попадают в разметку: в HTML уходят только тексты вариантов. Открыв DevTools, нельзя
понять, какой вариант ведёт в Слизерин. Приятный побочный эффект — подсчёт можно менять
без правки клиента.

### Оформление без единой внешней зависимости

Ночное небо — это девять слоёв CSS-градиентов, замок — инлайновый SVG, парящие свечи —
14 элементов с анимацией `float` + `flicker`, гербы факультетов — эмодзи. Ни одного
запроса к CDN, ни одного шрифтового файла, полная поддержка `prefers-reduced-motion`,
темы факультетов задаются CSS-переменными `--h1` / `--h2` прямо из данных сервера.

## Компромиссы

**`EnsureCreated()` вместо миграций EF Core.** Схема создаётся одним вызовом, а не
цепочкой миграций. Плюс: `git clone && dotnet run` работает без установки `dotnet-ef` и
без шага `database update`. Минус: изменить схему без удаления файла БД нельзя. Для
приложения, где все данные восстанавливаются из внешнего API за минуту, это выгодная
сделка; для проекта с пользовательскими данными выбор был бы обратным.

**LLM-чат с персонажами не реализован.** Он требует ключа провайдера. Класть ключ в
репозиторий недопустимо, а без ключа функция превратилась бы в неработающую кнопку на
публичном демо. Вместо одного показательного, но нерабочего пункта сделаны три
работающих: квиз Шляпы, хранилище артефактов и классификация заклинаний. Точка
расширения есть — сервис с интерфейсом и DI-регистрацией добавляется без правки
контроллеров.

**SQLite вместо Postgres/Supabase.** Описано выше: приоритет отдан воспроизводимости
запуска. На бесплатном хостинге с эфемерным диском счётчики коллекции сбрасываются при
редеплое (данные каталога — нет, они перезагружаются из API). Для продакшена достаточно
подключить том или заменить провайдер EF Core одной строкой в `Program.cs`.

**Без клиентского фреймворка.** React/Vue дали бы удобное управление состоянием списка,
но принесли бы npm, сборку и второй язык шаблонов ради трёх интерактивных сценариев.
Плата за отказ — примерно 550 строк ванильного JS, которые нужно писать аккуратно; выгода
— мгновенный первый рендер, работа без JS и отсутствие пайплайна сборки фронтенда.

**Фильтрация артефактов — на клиенте, персонажей — на сервере.** Артефактов 24, и они
целиком есть на странице: фильтровать их запросом к серверу было бы бессмысленной задержкой.
Персонажей 437 — там серверная пагинация обязательна. Одинаковый подход ради
«единообразия» проиграл бы обоим сценариям.

**Полное обновление вместо инкрементального.** Синхронизация каждый раз забирает весь
набор данных: внешний API не отдаёт «изменённые с» и не поддерживает ETag. При 437 записях
это ~180 КБ раз в 6 часов — оптимизировать нечего.

**Изображения грузятся с чужого хоста.** Портреты отдаёт `ik.imagekit.io` — тот же хост,
что использует внешний API. Проксировать их через себя означало бы кэш, диск и трафик ради
эстетики. Осознанное исключение из правила «всё через сервер»: это статические картинки,
а не сервис с данными.

## Известные проблемы и ограничения

1. **Холодный старт внешнего API.** `hp-api.onrender.com` живёт на бесплатном инстансе и
   засыпает после простоя. Первая синхронизация после долгой паузы может занять до
   минуты. Приложение не блокируется: оно стартует сразу, показывает статус
   `syncing`/`stale` и повторяет попытку. Но при самом первом запуске каталог около
   минуты может быть пуст.

2. **У части персонажей нет портрета.** Так во внешних данных: у некоторых записей поле
   `image` пустое, у некоторых URL отвечает 404. В обоих случаях показывается
   стилизованная заглушка 🪄 (для 404 — через глобальный перехват события `error`).
   Заметно, например, на карточке Альбуса Дамблдора.

3. **Счётчик коллекции считает браузеры, а не людей.** Идентификатор хранится в cookie,
   поэтому очистка cookie или режим инкогнито дают «нового посетителя». Это осознанная
   цена отказа от аккаунтов; накрутка одним браузером при этом заблокирована.

4. **Данные о факультете есть не у всех.** 135 персонажей из 437 имеют факультет во
   внешнем API. Остальные показываются как *Unsorted*; для них в фильтре есть отдельное
   значение.

5. **Счётчики не переживают редеплой на бесплатном хостинге.** См. компромисс по SQLite.

6. **Классификация заклинаний эвристическая.** Она построена на ключевых словах в имени и
   описании, потому что во внешних данных категории нет вовсе. Для нескольких заклинаний
   категория получается спорной (например, «Summons water» попадает в *Conjuration*).
   Это обогащение данных, а не канон.

7. **Одновременные нажатия могут разойтись со счётчиком на единицу.** Инкремент счётчика
   выполняется через EF Core без явной блокировки строки. При реальной нагрузке
   потребовалась бы транзакция с `UPDATE ... SET Count = Count + 1`; на ожидаемом трафике
   демо это не проявляется.

### Исправленные в ходе разработки ошибки

Обе найдены ручной проверкой в браузере и оставлены здесь как часть описания процесса:

- **Бесконечная прокрутка молча останавливалась после смены фильтра.**
  `IntersectionObserver` вызывает колбэк только при *изменении* пересечения. Если после
  подмены содержимого сетки сигнальный элемент оставался в зоне видимости непрерывно,
  нового события не приходило — и подгрузка навсегда замирала. Решение: после каждой
  загрузки приложение само измеряет положение сигнального элемента и продолжает, если тот
  всё ещё близко к экрану (`continueIfSentinelVisible` в `wwwroot/js/site.js`).

- **`background-attachment: fixed` на `<body>`.** Chrome перерисовывает такой фон на
  каждом кадре прокрутки, что заметно мерцало вместе с прилипшей шапкой, а iOS его
  игнорирует. Звёздное небо перенесено в фиксированный псевдоэлемент `body::before` —
  тот же вид, один слой композитора.

- **Форматирование по локали хоста.** Длина палочки выводилась как `10,75 inches` на
  русскоязычной машине. Культура приложения принудительно переведена на инвариантную,
  раз интерфейс английский.

## Деплой

Проект контейнеризован и не требует ни одной обязательной переменной окружения.

### Render (рекомендуемый путь)

1. Запушьте репозиторий на GitHub и сделайте его публичным.
2. На [render.com](https://render.com) → **New → Blueprint** → выберите репозиторий.
   Render прочитает `render.yaml` и соберёт `Dockerfile`.
3. Дождитесь сборки. Приложение само создаст базу и наполнит её из внешнего API.

Альтернативно: **New → Web Service → Docker**, порт Render передаёт через `PORT`,
приложение его учитывает.

### Railway / Fly.io / любой хост с Docker

```bash
docker build -t harry-potter-explorer .
docker run -p 8080:8080 -e PORT=8080 harry-potter-explorer
```

Чтобы счётчики коллекции переживали перезапуск, смонтируйте том в `/app/App_Data`.

### Проверка после деплоя

```bash
curl -s https://<ваш-домен>/api/stats
```

Ответ должен содержать `"characters": 437` и `"sync": { "state": "ready" }`.
Если `state` равен `syncing` — внешний API ещё просыпается, повторите через минуту.
